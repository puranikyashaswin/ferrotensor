How-to guide/Start here

Install Ferrotensor

Add the Rust crate, install the ferrotensor command, or install the Python package.

2 min readFerrotensor {{ft_version}}

  1. The tensor API, autograd, nn and optimizers, as a library in your Rust project.
  2. The ferrotensor command: LoRA train, eval, generate and info.
  3. The Python bindings. Wheels exist for macOS arm64 and Linux x86_64.

Follow the steps

  1. Install Rust 1.88 or newer with rustup. On macOS nothing else is needed: Ferrotensor uses Metal.

  2. On Linux, make sure a Vulkan driver is installed. NVIDIA's driver includes one; for AMD and Intel GPUs install Mesa (mesa-vulkan-drivers on Ubuntu).

  3. To use the tensor API in a Rust project, add the crate:

    cargo add ferrotensor

  4. To fine-tune and run language models from the terminal, install the command line tool. The binary is called ferrotensor:

    cargo install ferrotensor-cli

  5. For Python 3.10 or newer:

    pip install ferrotensor
More detail and options

On platforms without a wheel, pip builds the package from its source distribution, which needs Rust.

To work from a checkout instead:

git clone https://github.com/puranikyashaswin/ferrotensor.git
cd ferrotensor
cargo build --release -p ferrotensor-cli   # ./target/release/ferrotensor
pip install ./ferrotensor-py
Limits

DX12 on Windows and AMD and Intel GPUs have not been tested yet. If you try one, report what you find.

Check your GPU

See which GPU Ferrotensor will use and test its kernels against a CPU reference.

2 min readFerrotensor {{ft_version}}

  1. The version and platform you are running.
  2. Every adapter wgpu can open. The one marked * is the one Ferrotensor uses: name, vendor, device type and backend.
  3. The limits the kernels depend on. Large models need a large max buffer and storage binding.
  4. Each kernel is run on the GPU and compared with an f64 CPU reference. A line says ok or FAIL.

Follow the steps

  1. List the adapters:

    ferrotensor info

  2. Run the kernel check. Odd sizes are used on purpose, so tiling bugs show up:

    ferrotensor info --check

  3. If every line says ok, your GPU computes correctly with Ferrotensor. The command exits with an error when a kernel fails.

More detail and options

To try one backend only, set WGPU_BACKEND: vulkan, metal, dx12 or gl.

WGPU_BACKEND=vulkan ferrotensor info --check

For a bug report, ferrotensor info --check --json prints the same information as JSON. See Report results from your GPU.

Limits

The check covers matmul, softmax and RMSNorm, the kernels most likely to break on a new driver. The full GPU test suite is in Run the GPU tests.

Run your first program

A matmul and its gradient on the best available device, then the same idea in your own code.

3 min readFerrotensor {{ft_version}}

  1. Device::best() picked the GPU. Without one, the same code runs on the CPU.
  2. The forward result of the matmul.
  3. The gradient of the loss with respect to w, from loss.backward().

Follow the steps

  1. Clone the repository and run the example:

    git clone https://github.com/puranikyashaswin/ferrotensor.git
cd ferrotensor
cargo run --release -p ferrotensor --example quickstart

  2. In your own project (after cargo add ferrotensor), this trains a small network on XOR:

use ferrotensor::prelude::*;

let device = Device::cpu(); // or Device::best() for a GPU when present
let model = nn::Sequential::new(&device)
    .add(nn::Linear::new(2, 16, &device))
    .add(nn::Tanh)
    .add(nn::Linear::new(16, 2, &device));
let mut opt = optim::AdamW::new(model.parameters(), 0.05).weight_decay(0.0);

// XOR
let x = Tensor::from_data(&[0., 0., 0., 1., 1., 0., 1., 1.], &[4, 2], &device);
let y = Tensor::from_data(&[0., 1., 1., 0.], &[4], &device);
for _ in 0..200 {
    opt.zero_grad();
    let loss = F::cross_entropy(&model.forward(&x), &y);
    loss.backward();
    opt.step();
}
More detail and options

The example's source is ferrotensor/examples/quickstart.rs. The API reference is on docs.rs.

Limits

Tensors are f32 only. Very small models like this one run faster on the CPU than on a GPU; see Training is slow or uses too much memory.

How-to guide/Start here

Train a model from Python

PyTorch-style tensors, autograd, nn and optim from Python, on the CPU or a GPU. No NumPy needed.

3 min readFerrotensor {{ft_version}}

  1. The network's predictions for the four XOR inputs: all four are right.

Follow the steps

  1. Install the package:

    pip install ferrotensor

  2. Save this as xor.py and run python xor.py:

import ferrotensor as ft
from ferrotensor import nn, optim
import ferrotensor.nn.functional as F

model = nn.Sequential(nn.Linear(2, 16), nn.Tanh(), nn.Linear(16, 2))
opt = optim.AdamW(model.parameters(), lr=0.05, weight_decay=0.0)
x = ft.tensor([[0, 0], [0, 1], [1, 0], [1, 1]])
for _ in range(200):
    opt.zero_grad()
    loss = F.cross_entropy(model(x), [0, 1, 1, 0])  # XOR
    loss.backward()
    opt.step()
print(model(x).argmax(dim=1).tolist())
More detail and options

Tensors and layers take a device= argument. ft.Device("best") picks a GPU when there is one; ft.Device.gpu_available() tells you whether there is.

dev = ft.Device("best")
a = ft.randn(256, 256, device=dev)

ft.Device("gpu") raises RuntimeError when no adapter is found. Tensors on different devices cannot be mixed in one op; move them with .to(device).

Everything that is covered, and how it differs from PyTorch, is in the Python reference.

Limits

The Python API covers tensors, autograd, nn, optim and safetensors, not all of PyTorch. The LoRA fine-tuning tool is the command line, not Python.

How-to guide/Fine-tune a language model

Download a model and prepare data

Fetch a Llama-style checkpoint from Hugging Face and turn an instruction dataset into JSONL.

4 min readFerrotensor {{ft_version}}

  1. Each line is one example. Only the response tokens count toward the loss.
  2. An optional system message is used too. Prompts are wrapped in the ChatML template unless you pass --no-chat-template.

Follow the steps

  1. Install the Hugging Face command line tool:

    pip install huggingface_hub

  2. Download the model's weights, config and tokenizer:

    hf download HuggingFaceTB/SmolLM2-135M \
  model.safetensors config.json tokenizer.json tokenizer_config.json \
  --local-dir data/models/SmolLM2-135M

  3. Download the dataset:

    hf download yahma/alpaca-cleaned alpaca_data_cleaned.json \
  --repo-type dataset --local-dir data/alpaca-cleaned

  4. Convert it to {prompt, response} JSONL: keep short examples, shuffle with seed 0, and hold out 64 for evaluation.

    mkdir -p data/alpaca
python3 - <<'EOF'
import json, random
rows = json.load(open("data/alpaca-cleaned/alpaca_data_cleaned.json"))
out = []
for r in rows:
    p = r["instruction"].strip()
    if r.get("input", "").strip():
        p += "\n\n" + r["input"].strip()
    resp = r["output"].strip()
    if len(p) + len(resp) <= 500 and resp:
        out.append({"prompt": p, "response": resp})
random.Random(0).shuffle(out)
for name, rs in (("val", out[:64]), ("train", out[64:2064])):
    with open(f"data/alpaca/{name}.jsonl", "w") as f:
        for x in rs:
            f.write(json.dumps(x) + "\n")
EOF
More detail and options

For plain next-token training, use --task pretrain with .txt lines, JSON text or token arrays, or packed little-endian u32 .bin tokens.

Llama-architecture checkpoints have been measured: SmolLM2-135M, 360M and 1.7B. Sharded checkpoints load through model.safetensors.index.json.

Limits

Released LFM2 checkpoints are rejected because per-head q/k layernorm is not implemented yet.

How-to guide/Fine-tune a language model

Fine-tune a model with LoRA

Train a LoRA adapter with a response-only loss and check the held-out loss before and after.

5 min readFerrotensor {{ft_version}}

  1. The GPU in use. On a Mac this says Apple M2 (Metal).
  2. Only the LoRA adapters train: 921,600 parameters, rank 8 on q/k/v/o of every layer.
  3. Held-out loss of the base model, before any training.
  4. Seconds per optimizer step (8 sequences). tok/s counts response tokens only.
  5. The adapter, with its rank, alpha and targets in the file metadata, plus optimizer state for resuming.
  6. Held-out loss after 250 steps: 2.43 to 1.65.

Follow the steps

  1. Prepare a model and data as in Download a model and prepare data.

  2. Train. These are the settings of the measured run:

    ferrotensor train \
  --model data/models/SmolLM2-135M \
  --data data/alpaca/train.jsonl --eval-data data/alpaca/val.jsonl \
  --out data/runs/sft --seq-len 256 \
  --lr 5e-4 --warmup-steps 20 --grad-accum 8 --max-steps 250 \
  --log-every 10 --eval-every 50 --save-every 50 \
  --sample-prompt "Give three tips for staying healthy."

  3. Watch eval before and eval after. The run writes lora_adapters.safetensors, its .state.json, metrics.jsonl and training_state.json to --out.

More detail and options

Defaults that apply: batch size 1 (so --grad-accum 8 means 8 sequences per step), LoRA rank 8 and alpha 16 on q_proj,k_proj,v_proj,o_proj, gradient clipping at a global norm of 1.0, AdamW without weight decay, and warmup then cosine decay to lr/10.

  • --lora-rank, --lora-alpha and --lora-targets change the adapter.
  • --lite is a preset for small machines: sequence length 128, rank 4 and grad-accum 8, unless you set them.
  • --train-modules all|attn|mlp|norm|lm_head trains base weights instead of LoRA.
  • ferrotensor monitor follows a run's training_state.json in a terminal dashboard.

The same recipe on three model sizes on an NVIDIA A10G:

ModelHeld-out lossPer stepAdapter
SmolLM2-135M2.4250 → 1.65211.33 s3.7 MB
SmolLM2-360M2.0852 → 1.32281.69 s6.6 MB
SmolLM2-1.7B2.6474 → 1.06672.47 s12.6 MB

Every number, with the M2 run, is in the LoRA walkthrough.

Limits

Each step trains one sequence at a time (--batch-size only changes how many share an optimizer step). Tensors are f32. Models above 1.7B have not been tested.

How-to guide/Fine-tune a language model

Evaluate and chat with your adapter

Reload the adapter, measure the held-out loss, and generate text with or without it.

3 min readFerrotensor {{ft_version}}

  1. The adapter is applied on top of the frozen base model: 240 LoRA tensors.
  2. Reloading the adapter reproduces the held-out loss from training.
  3. Greedy output with the adapter. The base model repeats the prompt instead.
  4. Generation speed, with the KV cache.

Follow the steps

  1. Measure the held-out loss with the adapter:

    ferrotensor eval --model data/models/SmolLM2-135M \
  --data data/alpaca/val.jsonl \
  --lora data/runs/sft/lora_adapters.safetensors

  2. Generate, greedily:

    ferrotensor generate --model data/models/SmolLM2-135M \
  --lora data/runs/sft/lora_adapters.safetensors \
  --prompt "Translate 'good morning' into French." --temperature 0

  3. Run both again without --lora to compare with the base model.

More detail and options

generate takes --temperature (0 is greedy, default 0.7), --top-k (default 50), --top-p (default 0.9), --seed, --system, --max-new-tokens (default 128), --raw to skip the chat template, and --no-kv-cache. Greedy output is identical with and without the cache.

Limits

Small models stay small: answers are fluent but shallow, and sampled output can wander.

How-to guide/Fine-tune a language model

Resume or extend a run

Continue training from a saved adapter with its optimizer state and step counter.

2 min readFerrotensor {{ft_version}}

  1. Point --resume at an adapter a previous run saved; raise --max-steps to train further.
  2. The adapter, the AdamW moments and the step counter are restored. Batches already seen are skipped, in the same seeded order.

Follow the steps

  1. Keep the .state.json file next to the adapter. It holds the step and the optimizer state.

  2. Run the same command with a higher --max-steps and --resume:

    ferrotensor train --model data/models/SmolLM2-135M \
  --data data/alpaca/train.jsonl --out data/runs/sft --seq-len 256 \
  --lr 5e-4 --warmup-steps 20 --grad-accum 8 --max-steps 300 \
  --resume data/runs/sft/lora_adapters.safetensors
More detail and options

Use --save-every N during long runs so there is always a recent adapter to resume from.

Limits

The state file stores the AdamW moments as JSON, so it is large: 50 MB for SmolLM2-135M.

Run the whole recipe with one script

Download, train, evaluate and generate on any Llama-style model, and get one JSON summary.

3 min readFerrotensor {{ft_version}}

  1. Where it ran.
  2. Held-out loss before and after, on the same 64 examples as the walkthrough.
  3. Median seconds per optimizer step.
  4. Peak host memory of the training process.

Follow the steps

  1. From a checkout of the repository, install the Hugging Face tool:

    pip install huggingface_hub

  2. Run the script with any Llama-style model:

    scripts/lora-run.sh HuggingFaceTB/SmolLM2-360M

  3. Read data/runs/<model>/summary.json. It also has the loss curve and greedy generations from the base model and the adapter.

More detail and options

Options: --steps N (default 250) and --seq-len L (default 256). Everything else matches the walkthrough: 2,000 Alpaca examples, 64 held out, rank 8 on q/k/v/o, lr 5e-4.

Limits

The script needs bash, Python 3 and the hf command. It builds the CLI in release mode the first time.

Train an MLP with a DataLoader

Classic small-model training: Dataset, DataLoader, nn::Sequential, AdamW and a warmup-cosine schedule.

2 min readFerrotensor {{ft_version}}

  1. The examples default to the CPU. Set FERROTENSOR_DEVICE=gpu to use the GPU.
  2. 99.5% test accuracy on two noisy interleaved half-circles.

    cargo run --release -p ferrotensor --example mlp_two_moons

Train a small transformer from scratch

A two-layer GPT-style model built from nn layers, trained on Shakespeare sonnets and sampled.

3 min readFerrotensor {{ft_version}}

  1. nn::Embedding, nn::LayerNorm, causal nn::MultiHeadAttention and nn::Linear.
  2. The loss falls from 4.6 to 0.6 on training windows.
  3. With FERROTENSOR_DEVICE=gpu the same 600 steps took 31.9 s on the M2's GPU.
  4. Partly English-shaped, partly not: a working training loop on 3.7 KB of text, not a language model.

Follow the steps

  1. From a checkout:

    cargo run --release -p ferrotensor --example char_transformer
More detail and options

It uses AdamW, gradient clipping and a warmup+cosine schedule. Source: char_transformer.rs. More examples, with output, are in Use cases.

Limits

There is no held-out set, so the loss says nothing about generalisation.

How-to guide/Train your own models

Save, load and seed a model

Store parameters as safetensors and make random initialisation reproducible.

2 min readFerrotensor {{ft_version}}

  1. Seeds random tensors, layer initialisation and dropout, so a program gives the same numbers on every run.
  2. Writes every named parameter to a safetensors file.
  3. Loads them back in place. Loading is strict: missing or extra names are errors.

Follow the steps

  1. In Rust, use the three calls above. serialize::state_dict and load_state_dict give you the named tensors directly.

  2. In Python:

import ferrotensor as ft
ft.manual_seed(42)
model.save("xor.safetensors")
model.load("xor.safetensors")
More detail and options

Safetensors files load as F32, F16, BF16 or F64 (F32, F16 or BF16 in Python) and are converted to f32.

How-to guide/Performance

Choose a GPU and backend

Pick between the GPU and CPU, and between Metal, Vulkan, DX12 and GL.

2 min readFerrotensor {{ft_version}}

  1. Restricts which backends are tried: vulkan, metal, dx12, gl or a comma list. Applies to the library, the CLI and the tests.
  2. The CLI's --device: auto and gpu use the high-performance GPU; cpu uses wgpu's software adapter, which is slow.
  3. In Rust, Device::best() falls back to the CPU device; Device::gpu() returns None without a GPU.
  4. The examples read FERROTENSOR_DEVICE and default to the CPU.

Follow the steps

  1. Check what is available with ferrotensor info.

  2. On Windows, compare backends on the same GPU:

    WGPU_BACKEND=vulkan ferrotensor info --check
WGPU_BACKEND=dx12 ferrotensor info --check
Limits

One GPU per process. Multi-GPU training is not supported.

How-to guide/Performance

Turn on op fusion

Run chains of element-wise ops as one GPU dispatch. Results are bit-identical.

2 min readFerrotensor {{ft_version}}

  1. A chain of small ops takes half the time.
  2. A training step gets 21% faster.
  3. Ops that are not element-wise chains are unchanged.

Follow the steps

  1. Set the variable for any program that uses the ferrotensor Tensor API, Rust or Python:

    FERROTENSOR_DEVICE=gpu FERROTENSOR_FUSION=1 \
  cargo run --release -p ferrotensor --example char_transformer

  2. Results do not change: every intermediate is still written, and CI checks fused and unfused runs bit for bit.

More detail and options

Up to six consecutive same-size element-wise steps run as one fused dispatch. The design and its decision tree are in op fusion.

Limits

Off by default. It applies to the Tensor API, not to the LoRA command line, which uses its own kernels.

How-to guide/Contribute

Run the GPU tests

Check every kernel and gradient on your GPU against the CPU.

3 min readFerrotensor {{ft_version}}

  1. Every ferrotensor-backend kernel against a CPU reference. 229 GPU tests pass on an NVIDIA A10G and a Tesla T4.
  2. The Tensor API: forward values and gradients on the GPU must match the CPU.
  3. Finite-difference gradient checks of every autograd op on the GPU.

Follow the steps

  1. Clone the repository, then run the suites above. Without the variable, GPU tests skip themselves.

  2. Add FERROTENSOR_FUSION=1 to the second command to test op fusion too.

More detail and options

Every pull request runs these suites in CI on Mesa lavapipe, a Vulkan driver that runs on the CPU, so the Vulkan path is checked without a GPU. Behaviour on real hardware still needs a local run. Adding a kernel is covered in Writing a kernel.

Limits

Use --test-threads=1: creating several GPU devices at once is unreliable on some drivers.

How-to guide/Troubleshooting

No GPU found, or the wrong one

What to do when Ferrotensor runs on the CPU or picks an unexpected adapter.

2 min readFerrotensor {{ft_version}}

  1. wgpu could not open a GPU. Programs that use Device::best() or ft.Device("best") keep working on the CPU.

Follow the steps

  1. On Linux, install a Vulkan driver (NVIDIA's driver, or Mesa for AMD and Intel) and check with vulkaninfo --summary.

  2. If several adapters are listed, restrict the backend with WGPU_BACKEND, for example WGPU_BACKEND=vulkan.

  3. In a container or VM without GPU access, use the CPU device: Device::cpu(), ft.Device("cpu"), or --device cpu for the CLI.

Training is slow or uses too much memory

Why tiny models are faster on the CPU, and what the GPU memory limits are.

3 min readFerrotensor {{ft_version}}

  1. Before 0.5, parts of the backward pass and the loss copied tensors to the CPU and back: about 2,000 blocking reads per step.
  2. 0.5 keeps them on the GPU and batches dispatches. Update if you are on an older version.

Follow the steps

  1. Use the latest release: cargo install ferrotensor-cli --force.

  2. For very small models, use the CPU. Every GPU dispatch has a fixed cost, so a 1,218-parameter MLP trains about 10x faster on the CPU.

  3. Out of memory while loading a large model? SmolLM2-1.7B needed about 20 GB of host memory in 0.5. A fix that stops uploads from keeping a staging copy of every weight is on main and will be in the next release.

More detail and options

Try op fusion for Tensor API programs with long element-wise chains, and --lite for LoRA on small machines.

Limits

Tensors are f32 only, so memory is twice that of bf16 frameworks.
