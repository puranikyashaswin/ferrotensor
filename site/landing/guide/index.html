01 · Start here

Install Ferrotensor

Add the Rust crate, install the ferrotensor command, or install the Python package.

Ferrotensor {{ft_version}} · 2 min

  1. The tensor API, autograd, nn and optimizers, as a library in your Rust project.
  2. The ferrotensor command: LoRA train, eval, generate and info.
  3. The Python bindings. Wheels exist for macOS arm64 and Linux x86_64.

Steps

  1. Install Rust 1.88 or newer with rustup. On macOS nothing else is needed: Ferrotensor uses Metal.

  2. On Linux, make sure a Vulkan driver is installed. NVIDIA's driver includes one; for AMD and Intel GPUs install Mesa (mesa-vulkan-drivers on Ubuntu).

  3. To use the tensor API in a Rust project, add the crate:

  4. To fine-tune and run language models from the terminal, install the command line tool. The binary is called ferrotensor:

  5. For Python 3.10 or newer:

Details

On platforms without a wheel, pip builds the package from its source distribution, which needs Rust.

To work from a checkout instead:

git clone https://github.com/puranikyashaswin/ferrotensor.git
cd ferrotensor
cargo build --release -p ferrotensor-cli   # ./target/release/ferrotensor
pip install ./ferrotensor-py

Limits

DX12 on Windows and AMD and Intel GPUs have not been tested yet. If you try one, report what you find.

  2. Run the kernel check. Odd sizes are used on purpose, so tiling bugs show up:

  3. If every line says ok, your GPU computes correctly with Ferrotensor. The command exits with an error when a kernel fails.

Train a model from Python

PyTorch-style tensors, autograd, nn and optim from Python, on the CPU or a GPU. No NumPy needed.

Ferrotensor {{ft_version}} · 3 min

  1. The network's predictions for the four XOR inputs: all four are right.

Steps

  1. Install the package:

  2. Save this as xor.py and run python xor.py:

Details

Tensors and layers take a device= argument. ft.Device("best") picks a GPU when there is one; ft.Device.gpu_available() tells you whether there is.

dev = ft.Device("best")
a = ft.randn(256, 256, device=dev)

ft.Device("gpu") raises RuntimeError when no adapter is found. Tensors on different devices cannot be mixed in one op; move them with .to(device).

Everything that is covered, and how it differs from PyTorch, is in the Python reference.

Limits

The Python API covers tensors, autograd, nn, optim and safetensors, not all of PyTorch. The LoRA fine-tuning tool is the command line, not Python.

02 · Fine-tune a language model

Fine-tune a model with LoRA

Train a LoRA adapter with a response-only loss and check the held-out loss before and after.

Ferrotensor {{ft_version}} · 5 min

  1. The GPU in use. On a Mac this says Apple M2 (Metal).
  2. Only the LoRA adapters train: 921,600 parameters, rank 8 on q/k/v/o of every layer.
  3. Held-out loss of the base model, before any training.
  4. Seconds per optimizer step (8 sequences). tok/s counts response tokens only.
  5. The adapter, with its rank, alpha and targets in the file metadata, plus optimizer state for resuming.
  6. Held-out loss after 250 steps: 2.43 to 1.65.

Steps

  1. Prepare a model and data as in Download a model and prepare data.

  2. Train. These are the settings of the measured run:

  3. Watch eval before and eval after. The run writes lora_adapters.safetensors, its .state.json and .state.safetensors, metrics.jsonl and training_state.json to --out.

Details

Defaults that apply: batch size 1 (so --grad-accum 8 means 8 sequences per step), LoRA rank 8 and alpha 16 on q_proj,k_proj,v_proj,o_proj, gradient clipping at a global norm of 1.0, AdamW without weight decay, and warmup then cosine decay to lr/10.

  • --lora-rank, --lora-alpha and --lora-targets change the adapter.
  • --lite is a preset for small machines: sequence length 128, rank 4 and grad-accum 8, unless you set them.
  • --train-modules all|attn|mlp|norm|lm_head trains base weights instead of LoRA and saves the trained tensors, in f32, to trained_weights.safetensors. Pass that file to --lora in eval and generate, or to --resume with the same --train-modules.
  • ferrotensor monitor follows a run's training_state.json in a terminal dashboard.

The same recipe on three model sizes on an NVIDIA A10G (24 GB), 250 steps:

ModelHeld-out loss
SmolLM2-135M2.4250 → 1.6521
SmolLM2-360M2.0852 → 1.3228
SmolLM2-1.7B, f16 base weights2.6474 → 1.0640

Frozen base weights are stored as f16 by default, which saves GPU memory; for SmolLM2-1.7B the held-out loss moves by 0.0017 against f32 weights. --f32-weights keeps them f32. --checkpoint-blocks recomputes each decoder block during backward instead of keeping its activations: in 0.7, LoRA on SmolLM2-1.7B peaks at 8,222 MiB of GPU memory by default and 5,245 MiB with the flag, with the same printed losses and 39% more time per step. --batch-size N trains N sequences in one GPU pass with the same result, faster but with more GPU memory.

On the same GPU, PyTorch + PEFT on CUDA with the same recipe starts from the identical held-out loss and ends within 0.005 of Ferrotensor after 250 steps; Ferrotensor takes 1.2 to 3.1 times PyTorch's time per step.

Every number, with the M2 run and the full PyTorch comparison, is in the LoRA walkthrough.

Limits

Larger batches need more GPU memory; --checkpoint-blocks lowers it at the cost of time. Activations and LoRA adapters are f32. --q4-weights (4-bit base weights) is experimental and gives a worse held-out loss than f16. Models above 1.7B have not been tested.

04 · Performance

Choose a GPU and backend

Pick between the GPU and CPU, and between Metal, Vulkan, DX12 and GL.

Ferrotensor {{ft_version}} · 2 min

  1. Restricts which backends are tried: vulkan, metal, dx12, gl or a comma list. Applies to the library, the CLI and the tests.
  2. The CLI's --device: auto and gpu use the high-performance GPU; cpu uses wgpu's software adapter, which is slow.
  3. In Rust, Device::best() falls back to the CPU device; Device::gpu() returns None without a GPU.
  4. The examples read FERROTENSOR_DEVICE and default to the CPU.

Steps

  1. Check what is available with ferrotensor info.

  2. On Windows, compare backends on the same GPU:

Limits

One GPU per process. Multi-GPU training is not supported.

Run chains of element-wise ops as one GPU dispatch. Results are bit-identical.

Ferrotensor {{ft_version}} · 2 min

  1. Results are bit-identical with fusion on and off; speed has not been measured for this release.

Steps

  1. Set the variable for any program that uses the ferrotensor Tensor API, Rust or Python:

  2. Results do not change: every intermediate is still written, and CI checks fused and unfused runs bit for bit.

Details

Up to six consecutive same-size element-wise steps run as one fused dispatch. The design and its decision tree are in op fusion.

Limits

05 · Contribute

Run the GPU tests

Check the kernels and gradients on your GPU against the CPU.

Ferrotensor {{ft_version}} · 3 min

  1. Every ferrotensor-backend kernel against a CPU reference. 229 GPU tests pass on an NVIDIA A10G and a Tesla T4.
  2. The Tensor API: forward values and gradients on the GPU must match the CPU.
  3. Finite-difference gradient checks of every autograd op on the GPU.

Steps

  1. Clone the repository, then run the suites above. Without the variable, GPU tests skip themselves.

  2. Add FERROTENSOR_FUSION=1 to the second command to test op fusion too.

Details

Every pull request runs these suites in CI on Mesa lavapipe, a Vulkan driver that runs on the CPU, so the Vulkan path is checked without a GPU. Behaviour on real hardware still needs a local run. Adding a kernel is covered in Writing a kernel.

Limits

Use --test-threads=1: creating several GPU devices at once is unreliable on some drivers.

06 · Troubleshooting

No GPU found, or the wrong one

What to do when Ferrotensor runs on the CPU or picks an unexpected adapter.

Ferrotensor {{ft_version}} · 2 min

  1. wgpu could not open a GPU. Programs that use Device::best() or ft.Device("best") keep working on the CPU.

Steps

  1. On Linux, install a Vulkan driver (NVIDIA's driver, or Mesa for AMD and Intel) and check with vulkaninfo --summary.

  2. If several adapters are listed, restrict the backend with WGPU_BACKEND, for example WGPU_BACKEND=vulkan.

  3. In a container or VM without GPU access, use the CPU device: Device::cpu(), ft.Device("cpu"), or --device cpu for the CLI.

06 · Troubleshooting

Training is slow or uses too much memory

Why tiny models are faster on the CPU, and how to lower GPU memory.

Ferrotensor {{ft_version}} · 3 min

  1. The 0.6 baseline.
  2. 0.7 hands each intermediate gradient back once it is used and reuses freed buffers; on by default.
  3. --checkpoint-blocks recomputes each decoder block during backward: 19 to 39% more time per step.

Steps

  1. Use the latest release: cargo install ferrotensor-cli --force.

  2. Very small models train faster on the CPU, because every GPU dispatch has a fixed cost.

  3. If GPU memory allows, train several sequences per pass: --batch-size 8 --grad-accum 1 gives the same result as the default 8 steps of accumulation, 2.2x faster for SmolLM2-135M on an A10G.

  4. Out of GPU memory? Add --checkpoint-blocks, lower --batch-size, and keep the default f16 base weights. train --memory-report shows where the memory goes. SmolLM2-1.7B peaks at 5.3 GB of host memory with every option.

Details

Try op fusion for Tensor API programs with long element-wise chains, and --lite for LoRA on small machines.

Limits

Activations, gradients and LoRA adapters are f32; only frozen base weights are f16.
