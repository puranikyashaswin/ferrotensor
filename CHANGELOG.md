# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- A kernel that takes its sizes from its parameters binds the whole of a pooled buffer, so its bind group is reused when the pool hands the buffer to a tensor of another length in the same size class; only the kernels of kernels.wgsl that call `arrayLength` still bind a tensor's exact bytes. The bind group cache keeps 32,768 groups (was 4,096) and drops the oldest when full instead of emptying itself. Results are unchanged (the same held-out loss to every printed digit). On an A10G a SmolLM2-135M step at batch 1 × 8 takes 123.1 ms instead of 143.6 ms and 360M takes 146.3 ms instead of 163.7 ms; the 8 × 1 cases and 1.7B change by 1% or less. Bind groups reused per 135M step rise from 574 to 1,629 and the misses fall from 7,085 to 6,003.
- Up to 128 dispatches share a compute pass, up from 8: on an A10G a SmolLM2-135M step at batch 1 × 8 takes 124.6 ms instead of 143.6 ms and 360M takes 143.6 ms instead of 163.7 ms, with 1 to 3% less on the other four cases and the same losses ([measurements](benchmarks/RESULTS.md#passes-of-up-to-128-dispatches-20-november-2026)). `FERROTENSOR_PASS_DISPATCHES` still sets another value.

## [0.7.0] - 2026-11-19

Two behaviour changes to know before upgrading: `--train-modules layers.N` now matches layer `N` exactly, and `train --resume` with `--max-steps` at or below the saved step now trains nothing (both under Changed). `--q4-weights` is experimental and still fails its quality gate (under Added).

### Added
- GPU time by kernel from timestamp queries. `train --profile` adds to its median-step report a table of kernel name, dispatches, GPU milliseconds and share, sorted by GPU time, and to `profile.json` `kernel_timing`, `kernel_gpu_seconds_per_step` and `kernels` (`name`, `dispatches_per_step`, `gpu_seconds_per_step`). New `generate --profile` prints the totals and the table for the prefill and per decode token, and `--json` adds them under `profile`. Matmul is split by kernel (f32, f16 or 4-bit weights), layout and a size class. Timestamps go before and after each dispatch inside the usual passes when the adapter allows it (`inside_passes`), else at the start and end of one-dispatch passes (`pass_boundaries`); without timestamp queries one line says so and the totals print as before. They are read back at the waits the step already makes, and without `--profile` the device and the recorded work are unchanged. `info` shows each adapter's `kernel_timing`. Library: `KernelTiming`, `KernelTimingMode`, `KernelTime`, `KernelTimes`, `WgpuContext::try_new_with_timing`, `kernel_timing_mode` and `kernel_times`, and `AdapterReport::kernel_timing`.
- CI runs the GPU test suites through Metal on GitHub's Apple silicon runners (a virtualised GPU, `Apple Paravirtual device`) and through DX12 on WARP, Microsoft's software adapter; on WARP without the `ferrotensor-cli` end-to-end tests, which take too long there, and on pull requests only the backend kernel tests and the Tensor API parity tests (the full DX12 run, 2 h 22 min, is on `main`, weekly and by `workflow_dispatch`). Neither is a real-hardware result. `WGPU_DX12_COMPILER` (`dxc` or `fxc`) picks the DX12 shader compiler for `WgpuContext` and `Device::gpu`; CI uses DXC on WARP, where FXC took about 9 minutes to open the GPU. (#141)
- Experimental: tools to find where the 4-bit loss comes from; `--q4-weights` still fails its quality gate ([A10G run](benchmarks/RESULTS.md#4-bit-weights-the-gap-is-there-before-training)). `--q4-modules KEYS` and `--q4-skip KEYS` (on every command with `--q4-weights`, which they need) choose the linear weights stored at 4 bits with the `--train-modules` keys; the default `layers` keeps what `--q4-weights` stored before, every decoder-block projection, and `head` quantises `lm_head`, also when tied to the embedding. `--q4-group 16|32|64|128` (default 64) sets the weights per scale; the tensor carries the size and the matmul kernel reads it from the params word. `train` records the selection, group size and number of 4-bit tensors in `training_state.json`, the adapter's `.state.json` and `train --json` (`q4_weights`, absent without `--q4-weights`). `ferrotensor q4-report --model DIR [--q4-group N] [--json]` reads a checkpoint one tensor at a time on the host and prints, for every 2-D weight, the relative and largest error of the 4-bit round trip and the share of groups whose range one outlier sets. Library: `q4::Q4Group`, `q4::round_trip_error`, `UnifiedTensor::q4_group`, `model_builder::{Q4Selection, module_matches}` and `Lfm2ModelBuilder::with_q4_selection`; `q4::quantize`, `dequantize`, `packed_words` and `UnifiedTensor::from_f32_as_q4` take the group size. A 4-bit selection that matches no weight is a build error (exit code 2).
- `ferrotensor pretrain --tokenizer bpe --vocab-size N` (default 4096) learns a byte-level BPE tokenizer from `--data` before training: the 259 byte-level tokens at their ids, then one token per merge of the most frequent adjacent pair within the `ByteLevel` pre-tokenizer's words, a tie going to the lowest ids, so the same corpus and size give the same `tokenizer.json` and every text decodes back exactly. `--tokenizer byte` stays the default. A `--vocab-size` of 259 or less or above what the corpus can fill, `--vocab-size` with `byte`, a corpus that is not UTF-8, and a `--resume` whose saved tokenizer has another size than the flags ask for exit with 2; `--resume` reuses the saved tokenizer. `pretrain --json` adds `tokenizer`. Library: `ferrotensor_loader::tokenizer::train_byte_level_bpe`.
- `ferrotensor export-gguf --model DIR --out FILE.gguf` and `ferrotensor_trainer::gguf::export_gguf` write a Llama-style model as one GGUF version 3 file for llama.cpp and Ollama: 2-D weights in f16 and 1-D tensors and norms in f32 (`--f32` for all f32), llama.cpp tensor names, query and key rows reordered to llama.cpp's rotary layout, the `general.*` and `llama.*` metadata from `config.json`, and a byte-level BPE tokenizer (`gpt2` model, `gpt-2` or `smollm` pre-tokenizer) with its merges, special token ids and chat template. `--lora` adds an adapter while writing, with `merge`'s maths. It streams one row at a time, and refuses with exit code 2 an existing output, a non-Llama model, a config `check_supported` refuses (scaled RoPE among others), projection biases (Qwen2), a quantized base and other tokenizers. Written to the GGUF v3 specification; on one A10G run llama.cpp loaded the SmolLM2-1.7B file and matched the greedy completion of one prompt, two tokens (`scripts/check_gguf.sh`). The temporary file of the streaming writers is now `<file>.tmp`, the same name as before for `.safetensors` files.
- Qwen2 checkpoints load: a projection with a `<name>.bias` tensor gets that bias (`Linear::bias`, added on the GPU as `ones @ bias`, so its gradient flows when the base trains and it stays frozen under LoRA), and the RoPE base is read from `rope_parameters` when `rope_theta` is absent (the `transformers` 5 layout). CI generates a tiny random `Qwen2ForCausalLM` with `scripts/gen_qwen2_fixture.py` and checks its logits (full forward, KV-cache decoding, batched) and LoRA gradients against Hugging Face transformers (`ferrotensor-trainer/tests/qwen2_family.rs`). Qwen2.5-0.5B-Instruct loads on one A10G (held-out loss 1.3359).
- `ferrotensor pretrain --data corpus.txt --out DIR` trains a small byte-level Llama-style model from random weights and leaves `DIR` as a model directory that `generate --raw` loads: a 259-token byte-level `tokenizer.json` (`<pad>` 0, `<s>` 1, `</s>` 2, byte `b` as `b + 3`), an untied f32 model initialised from N(0, 0.02²) with a seeded generator, the corpus as `tokens.bin`, `train --task pretrain --train-modules full`, then the trained weights written as `model.safetensors` in the Hugging Face layout (the initial model lives in `DIR/init`; see Fixed). The training defaults are not tuned. `--resume` continues a run in the same directory. CI loads the result in Transformers and checks its loss against `eval`'s. Library: `ferrotensor_loader::tokenizer::byte_level_tokenizer_json` and `ferrotensor_trainer::pretrain` (`LlamaSize`, `write_random_llama`, `write_hf_weights`). (#126)
- The token embedding can train: `train --train-modules embed` trains only the embedding and `full` trains it with every base weight `all` selects (`all` is unchanged). `Tensor::embedding` gathers rows on the host and, when the table requires a gradient, records an `EmbeddingNode` whose backward scatter-adds each position's gradient into its row. `Lfm2Model::with_trainable_embedding` makes the table trainable (it is frozen otherwise, also when the other base weights train), and the lookup then reads the table back from the GPU each time; `Lfm2Model::clear_host_embeddings` drops the host copy after new values are loaded into a frozen table, as `eval --lora` and `generate --lora` do for trained weights that include it. A tied `lm_head` stays a separate copy. A `--train-modules` value that names the embedding by substring, such as `embed_tokens`, now trains it too; before, the optimizer received the table but it never got a gradient. (#124)
- `--model` of every command takes a Hugging Face model id such as `HuggingFaceTB/SmolLM2-135M` that is already in the local Hugging Face cache, as well as a directory; an existing directory wins. stderr shows `model: <id> (<snapshot>)` once, and an id that is not cached exits with 2 and names the cache and `hf download <id>`, as does a snapshot without `config.json` (an incomplete download). Nothing is downloaded. After a LoRA `train` or `finetune`, stderr ends with the `chat` and `merge` commands for the run. `FerrotensorHub::new` now follows Hugging Face's cache order (`HF_HUB_CACHE`, `HF_HOME`, `XDG_CACHE_HOME`, then `HOME` or `USERPROFILE`) instead of `HOME` alone, `find_latest_snapshot` returns the snapshot `refs/main` points to (else the smallest snapshot name, not an arbitrary one), and `FerrotensorHub::cache_dir` returns the cache directory. (#121)
- `ferrotensor chat` holds a multi-turn conversation with a base model or a LoRA adapter, one user message per line of stdin, with the sampling flags of `generate` (now shared through one flattened set). Each turn re-encodes the whole conversation in ChatML (`Tokenizer::encode_conversation`; `encode_chat` is its one-turn case). When the conversation no longer fits `max_position_embeddings` (now read into `Lfm2Config`) the oldest exchanges are dropped and the system message is kept; a message that does not fit alone, or a tokenizer without ChatML tokens, exits with 2. `--json` prints one object per reply, each on its own line. (#118)
- `ferrotensor merge` and `ferrotensor_trainer::merge::merge_adapter` write a standalone model directory with a LoRA adapter folded into the base weights (`W + alpha / rank * (A B)^T`, each weight in its own dtype), streaming one tensor at a time so host memory stays near one row plus the adapter. It accepts a Ferrotensor adapter file or a PEFT directory, refuses quantized bases and mismatched adapters, and gives a tied `lm_head` its own weight. `--json` prints the output directory and the tensor counts. CI loads the merged model in Transformers and checks its logits against Ferrotensor's within 1e-3. `WeightsContext::tensor_names` lists a checkpoint's tensors. (#117)
- `--json` on `finetune`, `train`, `eval` and `generate`: stdout carries one JSON object when the command ends (the training summary with the measured GPU peak, and for `finetune` the plan; the loss and perplexity; the generated text and token counts) and every other line goes to stderr. With `--json`, errors print `{"error": "..."}` on stdout. `AGENTS.md` documents each object, the exit codes and the one-command path for coding agents, and `llms.txt` indexes the docs. `plan`, `chat`, `merge` and `pretrain` have `--json` from their own entries. (#115)
- `ferrotensor finetune` runs `train` with the batch size, sequence length, gradient accumulation and block checkpointing that `plan` picks for this machine, except those given on the command line, and prints the plan to stderr first. It takes every `train` flag plus `--memory-mib`, `--vram-mib` and `--force`. A plan that does not fit exits with 2 and does not train unless `--force` trains the smallest configuration anyway; `--lite` is refused. (#111)

The budget is `--memory-mib`, `--vram-mib`, 60% of system RAM on a GPU that shares it, the `nvidia-smi` total on an NVIDIA GPU, or an assumed 4,096 MiB. The estimate is fitted to measured A10G peaks (see Changed). `--json` prints one object, and without `--model` the documented SmolLM2 sizes are listed. (#107)
- `train --profile` counts the GPU work of every optimizer step (dispatches, bind groups, uniform buffers, submits, synchronizes, uploads and readbacks) and, after the run, prints the step with the median wall time and writes `profile.json`. (#106)
- `ferrotensor export-adapter --format peft` and `ferrotensor_trainer::peft` (`export_peft_adapter`, `save_peft_adapter`, `load_peft_adapter`) write and read Hugging Face PEFT adapter directories for Llama-style models. `eval --lora`, `generate --lora` and `train --resume` accept a PEFT directory. - Experimental: a 4-bit (affine, groups of 64) weight format and a matmul that decodes it in `ferrotensor-backend` (#95), and `--q4-weights`, which stores frozen decoder-block weights at 4 bits; this changes the model's outputs. `--q4-weights` is experimental and still fails its quality gate: the untouched base model has a higher held-out loss with it than with f16. ### Changed
- Matmuls with a short output side run a thin kernel (`matmul_thin`, and `matmul_thin_h` for f16 `b`) instead of the 64x64-tile kernel: when the output has at most 64 rows (a short training pass against a weight, forward and input gradient, and LoRA products with few rows) or, for f32 `b`, at most 64 columns (LoRA products of rank up to 64, such as `x @ A`, run as the transposed product). A workgroup covers 8 rows by 32 columns and its threads split the inner dimension, reading f16 weights a word at a time. One-row `a @ b` keeps the matrix-vector kernel and 4-bit `b` keeps the tile kernel. Same maths with a different summation order. `--profile` names the new kernels with the size class `m<=64` or `n<=64`. On one NVIDIA A10G (Vulkan, builds interleaved, three runs each), a training step at sequence length 256 with batch 1 × 8 accumulation went from 1.193 to 0.961 s on SmolLM2-135M, 1.571 to 1.203 s on 360M and 2.233 to 1.697 s on 1.7B, and with batch 4 × 2 on 1.7B from 1.348 to 1.261 s. The training loss at step 30 is the same on both builds (135M 2.5320, 360M 1.8838, 1.7B 1.4793, also 1.4793 at batch 4 × 2), and the gradient norm at step 30 printed the same. A 250-step `finetune` of 1.7B (batch 4 × 2) went from 328.0 to 320.0 s with held-out loss 1.0612 on `main` and 1.0607 here (the summation order differs) and the same tracked peak, 14,061 MiB. Generation is unchanged. See [benchmarks/RESULTS.md](benchmarks/RESULTS.md#real-hardware-run-17-november-2026-thin-matrix-products-in-training).
- Decoding one token no longer runs the training kernels. A one-row `matmul`, `matmul_f16b` or `matmul_q4b` (every linear layer, `lm_head` and an unmerged LoRA adapter while decoding) runs a matrix-vector kernel whose workgroup threads split the inner dimension and read whole weight words (`matvec`, `matvec_h`, `matvec_q4`), and `flash_attention_v2_with` with one query runs `flash_attention_decode`, whose threads split the cached keys; same maths and options, with a different summation order. Greedy `generate`, `chat` and the training sample pick the token with `ComputeEngine::argmax_rows` on the GPU and read back token ids instead of the logits: per decode step, 4 bytes instead of 4 × vocabulary. Its tie rule is the host's: the largest value in `f32::total_cmp` order, the last index of equal maxima. Other sampling is unchanged. `Sampler::is_greedy` names the greedy case. On one NVIDIA A10G (Vulkan, builds interleaved, three runs each), greedy `generate` of 120 tokens went from 58.4 to 110.1 tokens per second on SmolLM2-135M, 39.8 to 96.7 on 360M and 18.9 to 56.9 on 1.7B, and sampled generation (`--temperature 0.7 --seed 7`) from 52.6 to 91.5 on 135M and 18.3 to 51.2 on 1.7B, and three-turn greedy `chat` on 1.7B from 18.9 / 17.1 / 15.7 to 56.7 / 55.0 / 53.4 per turn, with byte-identical greedy output; see [benchmarks/RESULTS.md](benchmarks/RESULTS.md#real-hardware-run-17-november-2026-generation).
- The monitor shows its clock in UTC (`HH:MM UTC`) and no longer depends on `chrono`, which RustSec marks unmaintained (RUSTSEC-2026-0543).
- `ferrotensor-backend` encodes up to 8 consecutive kernel dispatches into one compute pass instead of one pass per dispatch; a copy or a submission ends a pass early. wgpu-core 0.19 builds and drops usage trackers sized by the highest live buffer id for every pass, and longer passes delayed GPU work. On one NVIDIA A10G (same machine, builds interleaved), a training step with batch 1 × 8 accumulation at sequence length 256 went from 1.166 to 0.989 s on SmolLM2-135M, 1.547 to 1.334 s on 360M and 2.216 to 2.169 s on 1.7B. Greedy generation went from 40.6 to 59.5 tokens per second on 135M and from 16.1 to 17.5 on 1.7B. Loss and gradient norm are unchanged; on a 250-step 1.7B `finetune` with passes of up to 16 the tracked peak rose by 168 MiB. `GpuCounterSnapshot` and `train --profile` add `compute_passes` and `device_polls`. See [benchmarks/RESULTS.md](benchmarks/RESULTS.md#compute-passes-shared-by-consecutive-dispatches).
- Internal: the crates are published to crates.io from CI when a `v*` tag is pushed, with trusted publishing (no stored token), and a `Package` CI job runs `cargo publish --workspace --dry-run` on every pull request.
- The `plan` and `finetune` memory estimate is refitted on 9 peaks from a second card, an NVIDIA Tesla T4 (16 GB), with the 15 A10G peaks. The old one was 12.6% below SmolLM2-1.7B at batch 2 x 4 over 250 steps (11,138 MiB) and 13.1% below it at batch 8, sequence length 128, which filled the card. Accumulating runs keep growing past 30 steps (1.7B at 2 x 4: 9,541 MiB at 30 steps), so the estimate now targets the 250-step peak and adds 20% to activations when a step accumulates passes; activations count 0.92 times their f32 size plus 13 values per token and block per unit of key/value width; the fixed overhead is 1,600 MiB. It is at most 4.6% below all 24 peaks, at most 12% above the 250-step and single-pass peaks, and up to 35% above 30-step accumulating runs. The `plan` note says so.
- The docs record the T4 run of 16 November 2026 (main at `c7a0131`) in `benchmarks/RESULTS.md`.
- Behaviour change: `--train-modules layers.N` now trains layer `N` alone (an exact layer match) and `layers.A-B` layers `A` to `B`; before, `layers.1` also matched layers 10 to 19 as a substring. The keys are matched by `model_builder::module_matches`, shared with `--q4-modules`.
- Behaviour change: `train --resume` with `--max-steps` at or below the saved step now trains nothing and only saves, where it took one more step. For `pretrain` this exports the weights of an interrupted run. (#128)
- The docs record one run on a single NVIDIA A10G (24 GB) of 16 November 2026, a release build of `main` at `8b814c1`: `plan`, `finetune` with no memory flags for SmolLM2-135M, 360M and 1.7B and Qwen2.5-0.5B-Instruct, a 250-step SmolLM2-1.7B run (held-out loss 2.6474 to 1.0612) followed by `eval`, `merge`, `chat` and `export-gguf`, 4-bit losses of the untouched base models, `train --profile`, and byte-level `pretrain`. They replace the statements that these commands were only tested on software Vulkan, and keep the limits: one GPU, one run, and a two-token llama.cpp check. The tables are in `benchmarks/RESULTS.md`.
- The `plan` and `finetune` memory estimate counts the activations a decoder block keeps for backward from the autograd graph (every op output; flash attention keeps no scores, so the attention term is gone). `TrainConfig` gains `grad_accum`. The constants and the error bounds are in the refit above.
- `tokens_per_second` of `generate --json`, `chat --json` and the stats line on stderr is now the decode speed: one-token forward passes after the prompt, per second, with the prompt left out (null when none ran). It used to divide the new tokens by the prompt and decode time together, which understated decoding and, with the kept chat cache, changed with how much of each turn's prompt the cache held. The new key `prefill_seconds` gives the time to run the prompt, and the stats line shows both. After the last token `--max-new-tokens` allows, decoding no longer runs a forward pass whose logits nothing samples, so that token is not in the kept chat cache and the next turn runs it with the new message.
- `Lfm2Config::eos_token_id: Option<u32>` is now `eos_token_ids: Vec<u32>`, read from `eos_token_id` as one id or a list.
- `ferrotensor chat` keeps the KV cache across turns, so each turn processes only the new tokens: the new user message in the ChatML template, then the reply. The cache keeps the ids it holds; when a turn's encoding of the whole conversation does not start with them (old turns were dropped to fit the context, `/reset`, or the reply re-encodes to other ids) it keeps the longest common prefix and runs the rest, and it grows by copying when the conversation outgrows it. Greedy replies are the same as a full run of the conversation every turn (checked by a test). `--json` adds `cached_tokens`, the prompt tokens taken from the cache; `prompt_tokens` is still the whole conversation.
- `model_builder::check_supported` refuses a config whose `hidden_act` is not SiLU, whose `rope_scaling` or `rope_parameters` type is not `default` (an object with neither a type nor a `factor` counts as `default`), or that sets `use_sliding_window: true`, and the builder refuses an odd head size; before, such a model loaded and gave wrong logits. A `sliding_window` without `use_sliding_window` (Mistral-7B-v0.1) still loads, as Hugging Face applies no window there either. This refuses Llama 3.1 and later (`llama3` RoPE scaling). The CLI checks it right after reading `config.json`, and every model build error now exits with 2 instead of 1. `Lfm2Config` gains `hidden_act`, `rope_scaling`, `rope_parameters`, `sliding_window` and `use_sliding_window`.
- Every crate enables the workspace lints: `unsafe_code` is denied, and `missing_docs`, `unwrap_used`, `expect_used` and `panic` warn; CI runs clippy with `-D warnings`. (#108, #109, #110, #112, #114, #116)
- Inference no longer records an autograd graph: `generate`, `chat`, `eval`, the evaluation during `train` and classification predictions run their forward passes inside the new `ferrotensor_autograd::no_grad`, under which ops return tensors with no creator node, so intermediate activations are released as soon as the next op has been recorded. Training is unchanged. (#120)
- `ferrotensor` exit codes are the same for every command: 0 success, 1 runtime error, 2 invalid input or a request this machine cannot meet. Invalid input (a missing model, `config.json` or data file, a flag out of range, a dataset with no usable examples) and a missing GPU adapter (in `info` and in the commands that open the GPU) now exit with 2 instead of 1. `finetune` reports a plan that does not fit as `error: ...` instead of `finetune: ...`; the exit code stays 2. (#115)
- Backward keeps the first gradient each tensor receives instead of copying it into a new buffer. (#91)
- Backward releases each intermediate gradient once it has been used; after `backward` only leaves hold gradients, and a repeated `backward` adds exactly one more gradient per leaf. (#92)
- The buffer pool keeps buffers freed beyond its cap reusable until the GPU has finished the work recorded before them, then drops them and polls so wgpu destroys them at once (`FERROTENSOR_POOL_OVERFLOW=0` restores the old behaviour); the memory report's awaiting-GPU count now drops as submitted work finishes. (#93)
- Llama-style models name their block parameters as Hugging Face does (`input_layernorm`, `post_attention_layernorm`, `mlp.*` instead of `operator_norm`, `ffn_norm`, `feed_forward.*`); LFM2 models are unchanged. Adapter files and optimizer state with the old names still load. (#74)
- `apply_checkpoint` rejects adapter tensors the model does not have, instead of ignoring them. (#74)
- `Attention` has two new public fields, `q_norm` and `k_norm` (`None` for Llama), so struct literals need them. (#72)
- `mean_pool_matrix` takes a `skip_first` argument. (#73)
- `Optimizer::load_state` returns `Result<OptimizerLoad, String>` instead of `bool` (new public type `OptimizerLoad`), and `LoraMetadata` has a new public field `trained_modules: Option<String>`. (#76)
- A pretraining text line longer than `--seq-len` is now split into windows of at most `--seq-len` tokens instead of becoming one oversized example. (#78)
- The README, the LoRA walkthrough, the CLI README, the website and `CITATION.cff` state only measured results, with their conditions: the GPUs tested, the PyTorch comparison with its speed ratios, the gradient parity test and the GPU memory by stage. (#97)
- Loading a model uses less host memory: a tied `lm_head` is built without host copies of the transpose, checkpoint file pages are released as each tensor is read, and the host embedding table is filled from the checkpoint. Peak host memory for SmolLM2-1.7B LoRA training on an NVIDIA A10G went from 5,087 MiB to 1,575 MiB (5.33 GB to 1.65 GB), 360M from 1,762 to 1,200 MiB and 135M from 1,253 to 1,138 MiB, with identical losses. (#98)
- The docs and the website quote one confirmation run of merged `main` against the released v0.6.0 on one NVIDIA A10G: peak GPU memory for SmolLM2-1.7B LoRA is 11,671 MiB in 0.6.0, 8,142 MiB in 0.7 and 5,313 MiB with `--checkpoint-blocks` (+19% to +39% median time per step across the four measured settings). Within 0.7 the losses are identical with and without `--checkpoint-blocks`; against 0.6.0 they differ slightly because of the LoRA initialization fix below. The largest gradient difference against PyTorch autograd is below 1e-6 (9.5e-7 in that run). (#100, #101)

### Fixed
- `ComputeEngine::top_k` returned the top index twice on Metal (seen on Apple's paravirtual GPU in CI): the kernel read back the indices it had just written. It now keeps the previous pick in registers. (#141)
- `ComputeEngine::new` panicked with `matmul.wgsl changed` when built from a Windows checkout with CRLF line ends. (#141)
- The Tensor API's `tanh` and GELU kernels compute tanh from `exp`. With WGSL's built-in `tanh`, which DX12 compiles to HLSL `tanh`, the GELU and Tanh gradients on WARP were about 1e-3 off the CPU. The Tensor API tests share one GPU device per process; on WARP, creating one per test failed with `OutOfMemory` after about 20 devices. (#141)
- The four tests in `ferrotensor-trainer/tests/qwen2_family.rs` skip with a message when `FERROTENSOR_QWEN2_FIXTURE` is unset instead of failing, so `cargo test --release --workspace -- --ignored` runs to the end on a machine without PyTorch; a set but wrong path still fails, and CI sets the variable. `docs/testing-on-your-gpu.md` says how to generate the fixture.
- A `config.json` whose `eos_token_id` is a list (the form `generation_config.json` often uses) no longer fails to load; every id in it ends generation. A prompt in the ChatML template (`chat`, `generate` without `--raw`, the `train --sample-prompt` sample) also stops at `<|im_end|>` when the tokenizer has it, whatever EOS the config names; `--raw` keeps its stop set.
- The loader no longer hides errors behind a fallback. A Hugging Face tokenizer that fails to encode or decode returns the error instead of switching to the whitespace and character reader, and the CLI exits with 1 and names it; the plain reader is kept only for a `tokenizer.json` that is a bare `model.vocab` map with no model `type`, and a typed `tokenizer.json` the Hugging Face reader refuses is now an error. Probing for an optional tensor (`<name>.bias`, `q_norm`, a tied `lm_head`) reports a checkpoint file that no longer parses as an error instead of "absent". A refused `madvise` after reading a tensor is an error instead of being dropped. `FerrotensorHub::list_cached` reports an unreadable cache directory instead of listing nothing, and a cache path in an environment variable that is not UTF-8 is used instead of skipped. Public signatures that change: `Tokenizer::encode`, `encode_continuation`, `encode_chat` and `encode_conversation` return `Result<Vec<u32>, String>` and `Tokenizer::decode` returns `Result<String, String>`; `WeightsContext::get_tensor_info` returns `Result<Option<TensorMetadata>, LoaderError>` (was `Option<(Vec<usize>, String)>`); `ferrotensor_trainer::build_sft_example` returns `Result<Option<TrainingExample>, String>`; `FerrotensorHub::list_cached` returns `HubResult<Vec<String>>`.
- An interrupted `pretrain` no longer leaves a random model that loads as if trained: the initial model is written to `DIR/init` and training starts from it, so `DIR/model.safetensors` exists only once the trained weights are exported, and loading `DIR` before that fails with a message that names `pretrain --resume`. (#128)
- `--train-modules` values that select part of the base weights (`attn`, `mlp`, `head`, `embed`, a substring) now freeze the others (`Lfm2Model::with_trainable_base_weights`). Backward computed a gradient for every unselected weight and kept summing it across steps, one f32 buffer per weight that the optimizer never read. Gradient clipping summed only the selected gradients before and after, so losses, gradient norms and updated weights do not change; LoRA training is untouched. (#128)
- `generate` exits with 2 and a message when the prompt encodes to no tokens (`--raw --prompt ""` with a tokenizer that adds no BOS), where the forward pass got a zero-length sequence; `generate_tokens` now returns a `Result`, so `chat` and `train --sample-prompt` share the check. `generate` also reads `max_position_embeddings`: a prompt longer than it exits with 2, and a prompt plus `--max-new-tokens` beyond it lowers the new tokens to what fits and says so on stderr, instead of sampling past the trained context. (#123)
- `Tokenizer::bos_token_id` is the `bos_token` declared in the `tokenizer_config.json` beside `tokenizer.json` when it names a token, instead of always guessing `<|im_start|>`; the guess stays the fallback, and token ids from the Hugging Face tokenizer are unchanged because it never reads the field. A malformed `tokenizer_config.json` is now an error. The KV-cache attention output and `Embedding::forward` return frozen tensors, so cached logits of a frozen model no longer report that they require a gradient that could never arrive. (#122)
- The LFM2 conv block wrapped its output in a fresh leaf, so no gradient reached the conv weight, its bias or the input projection. `Tensor::conv1d` is differentiable now, with a WGSL backward kernel. (#105)
- The MLP example and the Python tests that depend on random values are seeded, so CI no longer fails on an unlucky initialisation. (#125, #127)
- `Architecture::detect` treated any config with `layer_types`, which recent `transformers` versions write for Qwen3, as LFM2. Llama-style layers other than full attention are now rejected. (#72)
- LoRA adapters of the same shape in one layer (for example `q_proj` and `o_proj`) no longer start from the same A matrix; every adapter's seed now depends on its layer and projection name. Initial adapters, and so LoRA runs, differ from earlier releases. (#75)
- `ferrotensor-cli train` with `--train-modules` other than `lora` now saves the trained base weights (f32, only the tensors that trained) to `trained_weights.safetensors`; before, it wrote an empty adapter file. `eval --lora`, `generate --lora` and `train --resume` load that file; an empty file from an older run is reported as such. (#76)
- `Optimizer::load_state` reports how many parameters got their saved state back and how many saved entries went unused. `train --resume` now fails when the saved optimizer state matches none of the trainable parameters and warns when it matches only some. A saved moment of the wrong shape is rejected. (#76)
- `save_lora_checkpoint` and `apply_checkpoint` report a tensor stored as f16 instead of writing or reading it wrongly. (#76)
- Model loading returns an error instead of panicking or accepting bad input: invalid config sizes, shard paths that leave the model directory, empty shard indexes, odd-sized quantization scales, empty or duplicate-id tokenizer vocabularies, and non-file or oversized JSON files. Error messages name the file. (#84)
- Attention dropout (`attention_dropout > 0` in `config.json`) now draws a different mask per training step, micro-batch, rank and layer from the trainer's run seed (`Trainer::with_dropout_seed`, `--seed` in `ferrotensor-cli train`) instead of one fixed mask, and evaluation and generation no longer apply it. New `forward_with_dropout` / `forward_batch_with_dropout` on `Attention`, `Lfm2Block` and `Lfm2Model`, and `ferrotensor_graph::dropout`. No change with dropout 0. (#89)
- Pre-quantized (MLX `.scales`) checkpoints are rejected instead of loaded wrongly. (#96)
- A machine with no usable GPU adapter, or a driver that refuses the device, no longer makes the CLI panic: it prints the reason and exits with code 1 (code 2 for a missing adapter since #115, see Changed). New `WgpuContext::try_new` and `try_new_with_options` return a `ContextError`; `new` and `new_with_options` still panic, now with the same message. (#113)
- `merge_adapter` removes the partly written `model.safetensors.tmp` when writing the merged weights fails, and returns the write error. (#119)

## [0.6.0] - 2026-11-12

### Added
- `benchmarks/baselines/pytorch_lora.py`: the LoRA walkthrough's recipe in PyTorch + PEFT (same split, chat template, response-only loss, truncation, LoRA init, optimizer, schedule, clipping and held-out metric), as a reference point for Ferrotensor's numbers on the same GPU.
- `scripts/lora-run.sh` takes `--batch-size`, `--grad-accum`, `--f32-weights` and `--name` (a suffix for the run directory), and records them in `summary.json`. `--help`, or an option given where the model belongs, now prints the usage instead of starting a run.
- Batched LoRA training: with `--batch-size N`, a Llama-style model now runs N sequences through the GPU in one forward and backward pass, right-padded to the longest, instead of one at a time. Each sequence still contributes its own mean-loss gradient (per-row weights in the new `ComputeEngine::masked_cross_entropy_weighted`) and optimizer steps fall after the same sequences, so the result matches the sequential path. New `Lfm2Model::forward_batch`, `Lfm2Model::supports_batching` and `masked_cross_entropy_batch`; LFM2 models with conv blocks keep training one sequence at a time.
- `--f16-weights` for `ferrotensor train`, `eval` and `generate`, and `Lfm2ModelBuilder::with_f16_weights`: frozen linear-layer weights (attention, MLP and `lm_head`) are stored as f16, half their memory, while activations, products, norms, embeddings and LoRA adapters stay f32. On by default: on an NVIDIA A10G, LoRA on SmolLM2-1.7B reached a held-out loss of 1.0640 with f16 base weights against 1.0657 with f32, using 11.9 GiB of GPU memory instead of 14.7 GiB and 2.38 s per step instead of 2.49. `--f32-weights` keeps them f32 (`--f16-weights` is still accepted). `Tensor::matmul` uses the f16 kernels when its right operand is an f16 tensor that needs no gradient.
- `ferrotensor-backend`: `UnifiedTensor::from_f32_as_f16` stores a tensor as f16 (two values per 32-bit word, half the memory), and `ComputeEngine::matmul_f16b` and `matmul_bt_f16b` multiply by such a weight matrix with f32 products and sums. The kernel unpacks with WGSL's `unpack2x16float`, so it needs no f16 shader extension and runs on every adapter.
- `ferrotensor-trainer`: `TrainingCheckpoint::save` writes the optimizer moments to an F32 safetensors file next to the JSON (`moments_path`), with the step in its header, instead of as JSON numbers. A SmolLM2-135M LoRA resume state goes from 50 MB to about 7.4 MB. `load` reads both layouts, and rejects a moments file from a different step (a crash between the two writes).
- A how-to guide on the website (`/guide/`): 19 step-by-step guides, from installing and checking your GPU to LoRA fine-tuning, training in Rust or Python, performance and troubleshooting. Each has the real output to expect, annotated, with the machine it came from.
- The LoRA walkthrough compares Ferrotensor with PyTorch + PEFT on CUDA on the same NVIDIA A10G and recipe: identical held-out loss before training, within 0.005 after 250 steps, at 84% of PyTorch's speed for SmolLM2-135M and 37% for SmolLM2-1.7B.

### Changed
- `ferrotensor-backend`: uploading tensors no longer keeps a host-side staging copy of every upload until the next GPU submission. `WgpuContext::note_upload` counts uploaded bytes and every 256 MiB (`UPLOAD_RELEASE_BYTES`) waits for the copies so wgpu frees them; `synchronize` now also submits pending uploads. Loading a model held a staging copy of all its weights (6.8 GB for SmolLM2-1.7B in fp32); in the CI test, uploading 768 MiB grew peak memory by 1536 MiB before and is bounded at under 1.6x now.
- The README, CONTRIBUTING, the GPU testing guide, the architecture notes and the website's benchmarks and LoRA pages describe the NVIDIA results, the software-Vulkan CI job and op fusion; the README no longer says the Python package is missing from PyPI.
- The LoRA walkthrough, the README and the how-to guide show the 0.6 results on an NVIDIA A10G: SmolLM2-135M with `--batch-size 8` at 0.57 s per step against 1.28 s one sequence at a time, the same held-out loss 1.6521; SmolLM2-1.7B with f16 base weights at held-out loss 1.0640, 2.38 s per step, 11.9 GiB of GPU memory and 5.33 GB of host memory (20.01 GB in 0.5).

### Fixed
- `ferrotensor` CLI: when the GPU runs out of memory, wgpu panics with "Parent device is lost" and no mention of memory. The CLI now adds a hint after such a panic: lower `--batch-size` (raising `--grad-accum`), shorten `--seq-len`, use `--lite`, keep the default f16 base weights.

## [0.5.0] - 2026-11-02

### Added
- LoRA results on an NVIDIA A10G for SmolLM2-135M, 360M and 1.7B in the LoRA walkthrough (`docs/examples/lora-sft.md`): held-out loss 1.6521, 1.3228 and 1.0667 after 250 steps, at 1.33, 1.69 and 2.47 s per step. With the GPU changes below, SmolLM2-135M on the A10G went from 20.2 s to 1.33 s per step; its held-out loss is 1.6521 (1.6519 before, as on an Apple M2).
- Kernel and Tensor API benchmark results on an NVIDIA A10G and a Tesla T4 through Vulkan in `benchmarks/RESULTS.md`, with op fusion off and on.
- `scripts/lora-run.sh MODEL` runs the LoRA SFT walkthrough on any Llama-style Hugging Face model with the walkthrough's data and settings and writes a JSON summary (held-out loss before and after, loss curve, seconds per step, peak memory, greedy generations).
- Op fusion, off by default: with `FERROTENSOR_FUSION=1`, consecutive same-size element-wise ops on the GPU run as one `fused` dispatch of up to six steps instead of one dispatch each, still writing every intermediate. Results are checked bit-identical to unfused runs. See `docs/design/op-fusion.md`.
- The `WGPU_BACKEND` environment variable (`vulkan`, `metal`, `dx12`, `gl` or a comma list) restricts which backends `Device::new`/`gpu`/`best`, `WgpuContext::new` and `ferrotensor info` try.
- CI runs the GPU test suites and the autograd finite-difference checks on Mesa lavapipe (Vulkan on the CPU) for every PR, so the Vulkan path is checked without a GPU.
- `scripts/hardware-report.sh` runs `ferrotensor info --check`, the kernel benchmarks and the Tensor API benchmarks and writes one JSON report, so every machine is measured the same way. CI runs it in quick mode on software Vulkan.

### Changed
- `ferrotensor-autograd`: the backward passes of RMSNorm and RoPE run on the GPU (`ComputeEngine::rms_norm_backward`, `ComputeEngine::rope_theta_inverse`) instead of reading the input, weight and gradient back to the host. LoRA training made about 2,000 blocking GPU-to-host reads per step through these two ops.
- **Breaking**, `ferrotensor-trainer`: `masked_cross_entropy` computes the loss and its gradient on the GPU (`ComputeEngine::masked_cross_entropy`) and reads back only one loss per position. Before, it read the whole `[seq, vocab]` logits to the host and uploaded a gradient of the same size, about 50 MB each way per SmolLM2 sequence. It now takes the `&ComputeEngine` as a fourth argument.
- `ferrotensor-backend`: `ComputeEngine` records kernel dispatches and copies into one pending command encoder on the `WgpuContext` and submits them together (every 128 ops, and when a tensor is read or written) instead of one queue submission per op. `WgpuContext::flush` submits the pending work; call it before submitting your own commands on `queue`. `WgpuContext::synchronize` waits for the GPU to finish.
- `ferrotensor-backend`: reading a tensor no longer blocks in wgpu's `Maintain::Wait`, which in wgpu-core 0.19 gives up after 5 s and frees the still-running submission's resources; it polls until the GPU is done.
- `ferrotensor-trainer`: the global gradient norm sums squares on the GPU (`ComputeEngine::sum_squares_partial`) and reads back once per optimizer step instead of once per gradient tensor.

### Fixed
- `ferrotensor`: waiting for the GPU no longer falls back to wgpu's blocking `Maintain::Wait`, which in wgpu-core 0.19 gives up after 5 s and frees the still-running submission's resources. A batch of more than 5 s of GPU work could crash the driver.
- The LoRA walkthrough called `target/release/ferrotensor-cli`; the binary has been `ferrotensor` since the rename.

## [0.4.0] - 2026-11-01

### Added
- `ferrotensor info` lists every GPU adapter wgpu can open (name, vendor, backend, driver, the limits the kernels depend on) and marks the one Ferrotensor uses. `--check` runs matmul, softmax and RMSNorm on it against an f64 CPU reference and exits non-zero if one is out of tolerance; `--json` prints the same for bug reports.
- `ferrotensor-backend`: `adapters::list_adapters` and `adapters::self_check`, the library side of `ferrotensor info`.
- A guide to testing Ferrotensor on other GPUs (`docs/testing-on-your-gpu.md`), and a field for `ferrotensor info --check --json` output in the bug report template.

### Changed
- `ferrotensor`: the backward passes of `index_select` and `nn::Embedding` scatter-add their gradients on the GPU instead of reading ids and gradients back to the host. The sums run in a fixed order, so the gradients are deterministic and match the CPU bit for bit.
- `ferrotensor`: `cat` concatenates on the GPU, and `cross_entropy` with class-id targets runs forward and backward on the GPU. On an Apple M2, `cross_entropy` over `[4096, 32000]` went from 749.6 ms to 64.6 ms on the GPU and from 4226.9 ms to 517.2 ms on the CPU, and an MLP training step from 3.69 ms to 2.13 ms on the GPU.
- `cross_entropy` with class ids computes the loss per row (log-sum-exp minus the target logit), so its last bits can differ from 0.3.0.
- The README feature matrix and the website list what is measured and what is not: the LoRA row now names SmolLM2-135M, the one model measured.

## [0.3.0] - 2026-10-26

### Added
- `ferrotensor`: `manual_seed(seed)` (also in the prelude) seeds the generator behind `Tensor::randn`, `rand`, `uniform`, every `nn` layer's initialisation and `functional::dropout`, so a program gives the same numbers on every run. Unseeded behaviour is unchanged. Python: `ferrotensor.manual_seed(seed)`.

### Changed
- `ferrotensor`: reducing a whole tensor on the GPU (`sum()` and the other full reductions) uses a two-pass workgroup tree instead of one thread for every element. On an Apple M2, `sum()` of `[4096, 4096]` went from 2169 ms to 1.19 ms.
- `ferrotensor`: `argmax` and `argmin` run entirely on the GPU, so they no longer split the batched dispatch. `argmax_dim(-1)` of `[1024, 4096]` went from 8.40 ms to 0.99 ms on an M2. Ties resolve to the same index as on the CPU.
- The website takes its version from the workspace `Cargo.toml` and shows the newest CHANGELOG release.

### Removed
- `ferrotensor-graph`: `FlashAttention::forward_multi_head` and `FlashAttention::multi_head_forward`, deprecated in 0.2.1. Use `forward` (it already splits heads), projecting the input yourself.

### Fixed
- The Python MLP training test seeds its weight initialisation, so it no longer fails on a rare unlucky start.

### Fixed

## [0.2.0] - 2026-10-22

### Added
- **Python bindings** (`ferrotensor-py`, published to PyPI as `ferrotensor`): `Device`, `Tensor` with autograd and operators (`@` for matmul), `nn` layers (Linear, Embedding, LayerNorm, RMSNorm, Dropout, activations, Sequential), losses, SGD and AdamW with LR schedules, and safetensors state dicts. abi3 wheels for CPython 3.10+ on macOS arm64 and Linux x86_64, type stubs, a pytest suite and an MLP example.
- `ferrotensor`: `Tensor::tril` and `Tensor::triu`; the causal mask is built with `triu`.
- `ferrotensor`: a KV cache for `nn::MultiHeadAttention` (`forward_cached` with `nn::KvCache`). Decoding one token at a time matches the full causal forward within 1e-5 on CPU and GPU; `char_transformer` samples with it.
- `ferrotensor`: `DataLoader::epoch_prefetched` gathers batches on a background thread, in the same order as `epoch`.
- GPU parity tests for every `nn` layer and for safetensors round trips; a Tensor API benchmark (`benchmarks`, `tensor-api` binary) for CPU and GPU devices.
- CI builds and tests the Python wheels on every push and publishes them to PyPI from `v*` tags through trusted publishing.

### Changed
- `ferrotensor`: GPU ops are batched into one submission and one compute pass per sync point, reuse freed buffers, and read back without wgpu's 1 ms sleep on Metal. On an M2, 100 small element-wise ops go from 10.6 ms to 0.82 ms and an MLP training step (784-256-10, batch 64) from 10.8 ms to 3.98 ms; `char_transformer` trains 600 steps in 31.9 s (was 105.0 s). Results are bit for bit unchanged.
- `ferrotensor`: `Embedding::forward` gathers on the GPU without reading the ids back. Ids outside `[0, vocab)` now give zero rows and no gradient on both devices (before: a panic, or row 0 for negative ids).
- `ferrotensor`: `cross_entropy`, `nll_loss`, `accuracy` and `one_hot` take `impl Into<Targets>`: an f32 tensor of class ids or a slice, array or `Vec` of `i64`, `i32` or `usize`. Negative ids are skipped everywhere, so `accuracy` now ignores `-100` rows like the losses. Existing call forms still compile.
- `ferrotensor`: `DataLoader` stacks batches into one preallocated buffer instead of cloning each sample (`Dataset::with_sample`). An epoch of 20k × 784 floats at batch 128 goes from 63,923 allocations (251 MB) and 11.3 ms to 2,043 allocations (63 MB) and 6.4 ms on an M2.
- The `ferrotensor-backend` examples are ported to the current API and check their results against a CPU reference.
- Docs: install lines, a Python quickstart, batched dispatch in the architecture guide, refreshed timings, and new good first issues.

### Removed
- `ferrotensor`: the `metal` and `vulkan` Cargo features (no code read them) and the unused dependencies on the internal LLM crates, serde, serde_json, memmap2, log, env_logger and criterion.

## [0.1.0] - 2026-10-21

First public version.

### Added
- `ferrotensor`: tensor API with a CPU device and a wgpu GPU device, reverse-mode autograd checked against finite differences, differentiable `nn` layers (Linear, Embedding, LayerNorm, RMSNorm, Dropout, activations), SGD/Adam/AdamW, gradient clipping, LR schedules (cosine with warmup), `Dataset`/`DataLoader`, and safetensors save/load of module state dicts.
- `ferrotensor-backend`: wgpu compute backend (Metal / Vulkan / DX12) with hand-written WGSL kernels: register-blocked vec4 matmul, Flash Attention v2 forward and backward with causal offset, sliding window, masks and dropout, softmax, RMSNorm, RoPE, int8 dequantization, and a capped buffer pool. Every kernel is tested against a CPU reference.
- `ferrotensor-autograd`: GPU autograd tape used by the trainer.
- `ferrotensor-graph`: Llama / LFM2-style blocks (attention with RoPE, SwiGLU MLP, RMSNorm, KV cache, LoRA linear layers).
- `ferrotensor-loader`: safetensors and tokenizer loading for Llama-style Hugging Face checkpoints.
- `ferrotensor-trainer`: LoRA SFT with response-only loss and chat template, next-token pretraining, AdamW, FP16 loss scaling, gradient accumulation, checkpoint save and resume.
- `ferrotensor` command-line tool (`ferrotensor-cli` crate): `train`, `eval` and `generate` with temperature, top-k and top-p sampling and a KV cache.
- `ferrotensor-hub` (Hugging Face Hub downloads) and `ferrotensor-monitor` (terminal dashboard).
- Benchmark suite with recorded results (`benchmarks/RESULTS.md`) and an end-to-end LoRA walkthrough on SmolLM2-135M (`docs/examples/lora-sft.md`).
- CI (rustfmt, clippy with `-D warnings`, tests on Linux and macOS, rustdoc, MSRV, cargo-deny), release workflow for `v*` tags, issue and PR templates, `SECURITY.md`, `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, architecture and kernel-writing guides.
